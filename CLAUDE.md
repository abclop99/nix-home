# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a **Home Manager** (Nix) configuration repository for a NixOS system. It manages user-level packages, dotfiles, and services declaratively as a flake. The system-level NixOS config at `/persist/etc/nixos` is a separate flake and does not import `home.nix`.

## Build & Apply Commands

Fish abbreviations expand automatically; the underlying commands are shown for reference.

```bash
# Apply the home-manager configuration
hm-switch
# → home-manager switch --flake /home/abclop99/.config/home-manager#abclop99 --specialisation (darkman get)

# Check for evaluation errors without applying
hm-build
# → home-manager build --flake /home/abclop99/.config/home-manager#abclop99

# Update flake inputs (nixpkgs, home-manager, catppuccin, NUR, etc.)
nix flake update
```

The Nix side has no tests or linters — use `nil` (Nix LSP) for in-editor diagnostics. The contrast-audit harness does:

```bash
# Run its test suite (from tools/contrast-audit/)
nix develop -c pytest
```

The devShell also carries chromium and the Fira Code Nerd Font, both needed for `--screenshot`. Run the harness itself with `nix run .#contrast-audit` (git-tracked files only — stage new ones first) or, while editing it, `nix develop -c python3 -m contrast_audit`, which uses the working tree.

`hm-build` writes a `./result/` symlink to the would-be generation; inspect the rendered output (e.g. `grep grace ./result/home-files/.config/hypr/hyprlock.conf`) before running `hm-switch` to verify config changes. Per-variant outputs land at `./result/specialisation/{light,dark}/home-files/…` — useful when a change is gated on `config.theme.variant`.

Note: `grep`/`grep -c` exits **1** on zero matches, so a chained `hm-build && … && grep -c … ` background command reports task status `failed` even when the build succeeded and `0` was the expected count — trust the printed count, not the exit status (or append `|| true`).

**`hm-switch` auto-targets the current darkman mode** via `--specialisation (darkman get)`. To force a different variant, expand the abbreviation in your prompt and edit `(darkman get)` to `light` or `dark` before running. If `darkman` isn't running, the substitution returns empty and the command fails — drop the `--specialisation` flag and invoke `home-manager switch --flake /home/abclop99/.config/home-manager#abclop99` directly. Query the current mode with `darkman get` (sandbox blocks the dbus call — needs disabling per-call).

## Inputs

All dynamic dependencies are pinned via `flake.nix`:

- `nixpkgs` → `github:NixOS/nixpkgs/nixos-26.05`
- `nixpkgs-unstable` → `github:NixOS/nixpkgs/nixpkgs-unstable` — used in `modules/packages.nix` for the up-to-date `claude-code` package (stable's lags; see the `unstable` group's comment there).
- `home-manager` → `github:nix-community/home-manager/release-26.05` (follows `nixpkgs`).
- `catppuccin` → `github:catppuccin/nix/v26.05` (follows `nixpkgs`). Catppuccin's upstream `flake.nix` otherwise pins its *own* moving channel-tarball nixpkgs, which forced the build-time `whiskers` Rust renderer (a `nativeBuildInput` of every catppuccin port, built from source — no `cache.nixos.org` binary, no upstream cachix) to recompile on flake updates that didn't touch our nixpkgs. `follows` dedups it; whiskers still recompiles once when `nixpkgs` itself is bumped.
- `nur` → `github:nix-community/NUR` — wired via overlay (`overlays.default`), so `pkgs.nur.repos.<author>.<pkg>` works.

`flake.lock` is committed and pins everything. Run `nix flake update` to bump them.

**Release-bump cache gotcha:** when bumping a nixpkgs release ref (e.g. `nixos-26.05`), `nix flake update` may lock to an intermediate branch commit — or reuse a *stale* cached rev — that sits between channel bumps and isn't fully on `cache.nixos.org`, triggering large source rebuilds (e.g. `wine`). Force a fresh resolve with `nix flake update nixpkgs --refresh` and confirm the lock matches the channel rev: `curl -sL https://channels.nixos.org/nixos-XX.YY/git-revision`.

**Auto-upgrade risk:** `services.home-manager.autoUpgrade` runs `nix flake update && home-manager switch --flake .` weekly. This advances **every** input on every run, including `nixpkgs-unstable` which tracks the `nixpkgs-unstable` branch — i.e. a moving branch with no stability guarantee. A bad upstream commit landed during the week will be auto-merged into the next switch with no human review. (The previous `home-manager-unstable`/`master` input — formerly imported to supply the unstable `claude-code` HM module — was the worst of these: it once advanced past a `lib.hm.strings.isPathLike` refactor that stable's lib lacked, breaking eval. It has since been dropped; the unstable `claude-code` package is now installed directly via `home.packages` in `modules/packages.nix` (no HM module at all).) The pre-flake setup had a narrower surface: `nix-channel --update` only refreshed `home-manager` (release branch, stable) and `nixpkgs-unstable`. The new fan-out is the price of locking everything.

**Recovery if a weekly upgrade breaks switch:** `~/.local/state/nix/profiles/home-manager-<N-1>-link/activate` runs the prior generation's activate script directly (no CLI needed). Then `nix flake update --override-input <bad-input> github:…<known-good-rev>` (or temporarily `services.home-manager.autoUpgrade.enable = false;`) until upstream stabilises.

To narrow auto-upgrade in the future: replace `useFlake = true;` with a custom user systemd service that runs `nix flake update nixpkgs home-manager catppuccin nur` (omitting `-unstable` inputs), so unstable inputs only advance when manually requested.

## GitHub API token

`nix flake update` re-fetches every `github:` input via the GitHub API. **Anonymous** requests are capped at **60/hour per IP** — exhausted by repeated `nix flake update` runs within the hour (and/or a shared/CGNAT IP pooling that 60) → `HTTP 403 API rate limit exceeded`. Authenticating raises the cap to **5000/hour**. All inputs are **public** repos, so the token needs **no scopes** — it only lifts the rate limit. This also fixes the unattended weekly auto-upgrade (which runs `nix flake update` under `set -euo pipefail` and otherwise hard-fails the switch when rate-limited).

The token is provided via a **relative optional include** in `home.nix`'s `nix.extraOptions` (`!include github-access-tokens.conf`), which pulls in a hand-created machine-local file:

**Per-machine setup** (once, out of band — keeps the secret out of git and out of the store). Create a **classic** PAT with **no scopes** and **"No expiration"** (Settings → Developer settings → Tokens (classic) → check nothing). No-expiry matters: an expired token 401s with **no anonymous fallback** and silently fails the headless weekly auto-upgrade until rotated — so avoid fine-grained/expiring tokens here even though they'd otherwise work. Then, in fish (keeps the token out of shell/Atuin history — this repo syncs Atuin, which records full command lines):
```fish
umask 077                                            # new files this session → 0600
read -s tok                                          # paste the PAT (hidden, not in history)
printf 'access-tokens = github.com=%s\n' "$tok" > ~/.config/nix/github-access-tokens.conf
chmod 600 ~/.config/nix/github-access-tokens.conf    # unconditional 0600 (in case it pre-existed)
set -e tok
```
The file is a plain 0600 nix.conf fragment beside the HM-managed `~/.config/nix/nix.conf` symlink; nothing else is needed in-repo. Rotate/revoke via GitHub if it ever leaks (a no-scope PAT grants no access, only rate-limit budget under your identity). Note `nix config show access-tokens` prints it in plaintext — don't paste that output into bug reports.

## Architecture

- **`flake.nix`** — Flake entry point. Declares inputs (see "Inputs" above), constructs `pkgs` with NUR overlay + `allowUnfree`, exposes `homeConfigurations.abclop99` with `extraSpecialArgs = { inherit inputs; }` so every module can take `inputs`.
- **`home.nix`** — Main HM module. Takes `{ pkgs, inputs, ... }`. Imports all sub-modules, declares core identity (username, XDG, SSH, fontconfig), sets `programs.home-manager.path = inputs.home-manager` so the CLI's `<home-manager/...>` lookups resolve to the flake input.
- **`modules/`** — Split by concern. Modules that need `inputs` take it explicitly (`packages.nix`); others stick with `{ pkgs, ... }:`:
  - `packages.nix` — All `home.packages` (categorized: fonts, cliTools, apps, gaming, mediaTools, unstable). The `unstable` group holds packages pulled from `inputs.nixpkgs-unstable` (currently just `claude-code`, installed bare — no `programs.claude-code` HM module, since no Claude config is managed through HM; pinned to unstable because stable's lags by weeks). Also enables the HM-managed `programs.zellij`/`zathura`/`mpv` (for Catppuccin theming).
  - `shell.nix` — Fish, Bash, Atuin, fzf, zoxide, Starship, pay-respects. Also defines the `hm-switch` / `hm-build` fish abbreviations.
  - `editor.nix` — Helix configuration.
  - `terminal.nix` — Kitty terminal.
  - `git.nix` — Git, delta, GitHub CLI, GPG, gitmoji config.
  - `services.nix` — Syncthing, MPD, udiskie, gnome-keyring, Thunderbird, HM auto-upgrade (flake-mode: `useFlake = true; flakeDir = …`).
  - `hyprland.nix` — Hyprland window manager, keybindings, eww bar (via the `eww-bars` user unit, not an `exec-once` — see "Module quirks"), hyprlock, hypridle. Imports host-specific extra binds from `private/hyprland.nix` (skip-worktree'd: empty-`extraBinds` placeholder in git, real binds on disk) and appends them to `settings.bind`.
  - `theme.nix` — Catppuccin theme (Latte/Frappe) with darkman auto-switching via HM specialisations; darkman scripts hardcode `--flake /home/abclop99/.config/home-manager#abclop99`; reads coordinates from `./private/location.nix`. Exposes a read-only `config.theme.palette` attrset (e.g. `palette.mauve`, `palette.subtext0`) for theme-conditional logic in other modules; pattern: `let isLight = config.theme.variant == "latte"; in lib.optionalString isLight "…"`.
  - `firefox.nix` / `librewolf.nix` — Browser configurations with extensions and settings (firefox uses `pkgs.nur.repos.rycee.firefox-addons`).
  - `vscode.nix` — VS Code extensions and settings.
  - `starship.nix` — Starship prompt configuration (imported as a value, not a module).
- **`nixpkgs-config.nix`** — Minimal shared nixpkgs config (just `allowUnfree = true;` — NUR is added via overlay at the flake level, not via `packageOverrides`).
- **`files/`** — Static config files managed via `xdg.configFile` or `home.file`:
  - `eww/` — Eww widget bar (yuck/scss) with scripts for workspace/audio/window info. `scripts/sync-bars` is the odd one out: it is not a widget data source but the reconciler that opens one bar per connected monitor.
  - `firefox/` — Custom CSS (tree-style-tab).
  - `fontconfig/` — Font configuration.
  - `swaylock/` — Custom swaylock effect (C source).
- **`private/`** — Five tracked-but-skip-worktree files (`location.nix`, `ssh/config`, `gpg-key-fingerprint`, `rustdesk.nix`, `hyprland.nix`). The committed content is a placeholder; real values live only on disk. See "Private files" below.
- **`hooks/pre-commit`** — Tracked git hook that rejects commits with staged changes to the `private/` files. Activated per-clone via `git config core.hooksPath hooks`.

## Conventions

- Commit messages use **gitmoji** format (emoji prefix, e.g. `✨`, `🔧`, `👽️`) with a scope in parentheses (e.g. `hypr`, `firefox`, `home`, `eww`, `helix`). Scope = module/area name.
- Commits should be atomic (one logical change each). Non-obvious changes should have a reason in the commit body.
- The configuration targets NixOS 26.05 with Home Manager state version 23.11.
- Several 26.05 default-value changes are pinned to their pre-26.05 values (because state version stays 23.11); see [`docs/26.05-pinned-defaults.md`](docs/26.05-pinned-defaults.md) for the inventory and how to adopt each later.
- `inputs.nixpkgs-unstable` is used selectively (e.g., `claude-code.nix`) for packages needing newer versions.
- Nix experimental features `nix-command` and `flakes` are enabled.
- Default editor is Helix (`hx`), default shell is Fish.
- Keyboard layout is **Norman** — hyprland keybindings use `n/i/o/h` instead of `h/j/k/l`.
- Theme is **Catppuccin** — Frappe (dark) / Latte (light), auto-switched by darkman; variant exposed as `theme.variant` in `modules/theme.nix`.

## Private files

`private/{location.nix,ssh/config,gpg-key-fingerprint,rustdesk.nix,hyprland.nix}` are tracked but `--skip-worktree`'d. The committed content is a placeholder; real values live only in the working tree.

**Per-machine setup (after fresh clone):**
1. `git config core.hooksPath hooks` — activates the pre-commit guard.
2. `git update-index --skip-worktree private/location.nix private/ssh/config private/gpg-key-fingerprint private/rustdesk.nix private/hyprland.nix` — tell git to ignore local edits.
3. Populate real content (via `cat > private/foo` or your editor; the Claude `block-private.sh` hook blocks Edit/Write/MultiEdit, so use Bash or an editor outside Claude).

**Updating placeholder structure** (e.g., adding fields): edit the file, `git add private/foo`, `git commit --no-verify` (the hook would otherwise refuse). Then re-apply skip-worktree if necessary and restore real content.

**Adding new private files**: update both the `SKIP_WORKTREE_FILES` array in `hooks/pre-commit` AND run `git update-index --skip-worktree <new-file>` for each. The two sides are independent — the hook blocks accidental disclosure, the index flag makes git ignore local edits.

**Caveats:**
- `git reset --hard`, `git checkout` between branches, and `git stash pop` can silently flip skip-worktree off or overwrite on-disk real content with the placeholder. If `cat private/location.nix` ever shows zeros after a git operation, restore from a backup or re-edit.
- Skip-worktree'd files are sourced from the **working tree** by the flake's `git+file:` fetcher, but nix caches that snapshot under a key of `<HEAD-rev>;d=<hash of git-visible changes>` (`sourcePathToHash` rows in `~/.cache/nix/fetcher-cache-v4.sqlite`). Skip-worktree files are invisible to `git status`, so **they can never invalidate that key** — editing `private/*` alone leaves every later eval serving the cached tree, and `hm-switch` silently keeps applying the old values. Diagnostic tell: the stale value is the *previous real* value, not the committed placeholder — the snapshot did read the worktree, only invalidation is broken. Confirm by comparing the worktree file against `<flake source path>/private/<file>` (get the path from `nix flake metadata`).
- **What busts the cache:** any real content change to a git-visible tracked file (e.g. `nix flake update` rewriting `flake.lock` — verified 2026-08-12), a commit (new rev ⇒ new key namespace), or deleting the cache row. **What does NOT:** `--refresh` (on `nix flake lock` or `nix flake metadata`), `touch`ing the file, or `--option eval-cache false` — all three re-serve the identical stale store path.
- Old snapshots stay cached **forever under their key**, so whenever the git-visible dirty state returns to a previously-seen combination, nix replays that entire old tree — `private/*` content included. E.g. a `git checkout flake.lock` or a stash/pop that lands back on an earlier dirty state restores that snapshot's private values with nothing in the output saying so.

## Module quirks

- `programs.eww.configDir = <derivation>` makes `~/.config/eww` a symlink to a generation-specific store path; eww-server's socket name is hashed from the resolved path, so it changes on every switch and breaks `eww reload`. Use per-file `xdg.configFile."eww/<file>"` entries to keep the directory stable.
- `catppuccin.enable = true` (from catppuccin/nix) auto-enables every per-app submodule and trips assertions against existing `qt.platformTheme = "gtk"` and firefox extension config. Opt in per app: `catppuccin.<name>.enable = true`.
- Eww uses `grass` for SCSS, which errors `unknown @ rule: @charset "UTF-8";` on any non-ASCII source. Keep `files/eww/eww.scss*` pure ASCII.
- **One eww bar per monitor, and no monitor is named anywhere.** `scripts/sync-bars` diffs `hyprctl monitors -j` against `eww active-windows`, opening `bar-<monitor name>` for each monitor lacking one and closing bars whose monitor is gone, then re-runs on `monitoradded*`/`monitorremoved*` from socket2. Any display, any number, hotplug included — nothing to edit. `eww active-windows` (which prints `<id>: <window-name>`) is the **only** way to see whether reconciliation is correct; expect exactly one `bar-<monitor>` per connected output.
- **eww variables are global, not per-window** — that is the whole reason the bar data is shaped the way it is. A second bar would otherwise mirror the *focused* monitor's state, so `get-active-workspace` and `get-window-title` emit JSON keyed by monitor name and the widgets index it with the `screen` window argument (`active_workspaces?.[screen]`). `screen` is an eww *magic* window arg, auto-populated from `eww open --screen`, so it never needs `--arg`. `get-workspaces` stays a flat global 1-10 list because workspaces are shared across monitors, but each entry carries the `monitor` that owns it, so a bar can tell its own workspaces from the other monitor's. eww's `==` compares string-backed `DynVal`s, so the JSON number `5` and the string `"5"` from `get-workspaces`' `map(tostring)` still match — don't "fix" that mismatch.
- **The bar runs as the `eww-bars` user unit, not an `exec-once`.** `systemctl --user restart eww-bars` is a *full* config reload, stronger than `eww reload`: `ExecStartPre=-eww kill` drops any daemon the unit doesn't own (a daemon holds its config parsed in memory, so a leftover one serves the **old** widget tree to newly opened bars), and eww's daemon inherits the unit's cgroup, so stopping the unit takes the bars with it. Two settings that look wrong but aren't: `Restart=always` rather than `on-failure`, because the script's socat tail exits **0** when the Hyprland socket closes and `on-failure` would strand the unit inactive with the bars dead; and **PATH is inherited, not pinned** — eww launches its own listeners as `bash ./scripts/…`, and those reach for `brightnessctl`, `pamixer`, `pactl`, `python`, `jaq`, `socat` and `seq`, so pinning means maintaining that list forever and silently breaking a widget when it drifts. `HYPRLAND_INSTANCE_SIGNATURE` is available to the unit because Hyprland's first `exec-once` runs `dbus-update-activation-environment --systemd` *before* starting the session target.
- **What `hm-switch` reloads versus what it restarts — measured, not assumed.** Every file in `~/.config/eww` is a symlink into **one aggregate `home-manager-files` derivation**, and that aggregate is **profile-wide** — so editing `modules/git.nix` repoints `eww.scss` too, and the bars reload. eww's filewatch matches only paths ending `.yuck`/`.scss`/`.css` **and only `Modify(_)` events**, so the scripts directory can *never* trip it directly; the re-point of the yuck and scss is what does. That re-point registers at all only because **Home Manager's activation coreutils** runs `ln -Tsf` as symlink-to-temp plus `renameat`, which arrives as `IN_MOVED_TO` → `Modify(Name)` — a plain unlink+symlink would emit `Create`/`Remove` and be ignored. (Do not re-check this with the interactive `ln`: that is uutils here, and it *does* unlink+symlink, giving the opposite answer.) A reload then calls `stop_all()` on the script vars before re-initialising, respawning **every** `deflisten` child. Verified with a comment-only edit to `get-workspaces` whose rendered scss and yuck were byte-identical (`cmp` clean): every `get-*` listener took a new PID while the daemon kept its own. So the listeners were never the problem. **`sync-bars` is** — it is the unit's own `ExecStart`, not something eww launches, so no reload can touch it; it held one PID at `NRestarts=0` across three switches, one of them a darkman transition. That is what `Unit.X-Restart-Triggers = [ "${config.xdg.configFile."eww/scripts".source}" ]` covers, and it makes the restart guaranteed rather than a side effect of HM's bundling. sd-switch acts because the field **is not on its ignore list** — `Description` and `Documentation` are ignored, and every other key is significant whether `X-`prefixed or not (an arbitrary `ZzzUnknownKey` stop-starts too); it is *not* a raw text diff, and sd-switch 0.6.3 has no special case for the name. `X-Reload-Triggers` would be actively wrong: it selects the reload path and the unit is `CanReload=no`. **Tracked files only** — an untracked new script neither deploys nor triggers a restart, and is not even reported dirty, so `git add` it first (same rule as `nix run .#contrast-audit`). Scoped to the scripts on purpose: the scss is generated per specialisation, so including it would fire this twice a day; the rendered unit is byte-identical under `./result/specialisation/{light,dark}/`. **A simpler alternative exists, not taken:** `ExecStart` names `${config.xdg.configHome}/eww/scripts/sync-bars`, a `$HOME` path that never changes — which is *why* the unit text would not otherwise move when the scripts do. Pointing it at `${config.xdg.configFile."eww/scripts".source}/sync-bars` instead would make the unit change **whenever** the scripts change, at the same granularity and with the same specialisation-independence, retiring the dependence on sd-switch's ignore-list semantics entirely. Left alone because the trigger above is already verified and working; worth taking if this unit is touched again.
- **darkman's switch scripts run `eww reload || true` after `home-manager switch`** (`modules/theme.nix:303`, `:312`). The bars would reload anyway — a specialisation swap repoints `eww.scss`, which trips the watcher — so this is belt-and-braces, not the cause; the journal shows **two** reloads on a darkman transition (42s apart in one, 7s in another). Either way a theme transition proves **nothing** about eww's file watching, so any experiment about what a switch does to the bars must use a manual `hm-switch`, never a `darkman toggle`. That confounder is what made an earlier reading of the watcher wrong.
- **eww scripts must use `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/.socket2.sock`.** The legacy `/tmp/hypr/…` path no longer exists, and the failure is **silent**: socat exits immediately, the `deflisten`'s initial value is all eww ever receives, and the widget freezes at its startup value with nothing logged. `get-window-title` carried that bug for a long time (fixed in `3c2d8e3`). Diagnose with `pgrep -af 'scripts/get-'` — a working listener has a live process, a broken one has none. Note a script whose body is `socat … | while read` shows **two** bash processes (the script plus the pipeline subshell); that is normal, not duplication.
- **Per-monitor workspace sets were priced and rejected — don't re-raise.** Workspaces stay one shared global 1-10 pool, so a second monitor borrows one; `$mod CTRL, {n,i,o,h}` (`movecurrentworkspacetomonitor`) moves one between monitors. Rejected alternatives: native `workspace = N, monitor:…` rules (fixed split; best unplug story, since absolute binds never orphan anything), a wrapper script resolving `$mod+N` against the focused monitor (no plugin, but a subprocess per keypress, and workspaces 11-20 survive an unplug with windows intact yet become keyboard-unreachable), and `hyprlandPlugins.hyprsplit` — purpose-built, but nixpkgs pins **0.54.2** against Hyprland **0.55.4**, `cache.nixos.org` 404s its narinfo while `hy3` 0.55.0 returns 200 (so it builds from source, and whether 0.54-era C++ compiles against 0.55.4 headers is untested), and upstream calls the C++ plugin deprecated in favour of a Lua version needing `configType = "lua"` — the rewrite this config defers.
- **Scrolling a bar is monitor-constrained; clicking is not.** `hyprctl dispatch workspace` follows a workspace to whichever monitor holds it and drags the cursor along, so unconstrained scrolling of the shared pool walks you onto the other screen mid-gesture. `change-active-workspace` takes the bar's monitor as a third argument and steps only to workspaces that monitor owns plus ones that do not exist yet (no owner ⇒ claimable from any bar), with no wrap — at either end it stays put. Clicking is left alone on purpose: a workspace the bar shows dimmed as living elsewhere is one you can *see*, so clicking it is an explicit request to cross over. The workspace classes say where a workspace lives, not how full it is — `empty` means it does not exist, `occupied` is on this monitor, `elsewhere` is on another, coloured down Catppuccin's own `$text`/`$subtext0`/`$overlay0` ramp so "elsewhere" never reads as "empty".
- **Each listener filters socket2 by event prefix, and `workspace*` does not match `moveworkspace>>`.** Socket2 carries every event — unfiltered, every line cost 4 `hyprctl` processes, and only `get-window-title` wants the busy ones. `moveworkspace*` has to be listed separately wherever ownership or monitor keying matters. **Hyprland posts the v1 and v2 form of an event as separate lines**, so count in lines, not user actions: a bare focus change is 2 lines, a title change on the *focused* window is **4** (`windowtitle`, `windowtitlev2`, `activewindow`, `activewindowv2`) and 2 on an unfocused one, and a workspace switch matches *two* listeners because `workspace*` sits in both `get-active-workspace` and `get-window-title`. `get-window-title` matches those two families on their **v2 form only**, which is safe because of a pairing invariant and **not** redundancy — the families do not back each other up, and all seven emission sites in 0.55.4 post v1 and v2 as adjacent unconditional statements, so v2 never fires without v1 — re-verify on a Hyprland bump by checking each `…v2` emission still sits adjacent to an unconditional v1, because a v2-only site would silently starve the *unfocused* monitor's bar, which `windowtitlev2` alone drives. `openwindow`/`closewindow` keep plain globs because they have **no v2 sibling**; `movewindow` has one and stays doubled, as do the workspace and monitor events, because they are rare and a wrong glob silently freezes a widget. `get-workspaces` watches the monitor events *because* it carries ownership: an unplug migrates workspaces and would otherwise leave the indicator naming a monitor that is gone. **Measured, with the conditions that produced it** — 104 lines per 25s *while one terminal animated its title about once a second*; a genuinely idle desktop delivers **zero** — the filter takes `get-window-title` from 104 wakes to **52**, and `get-workspaces` and `get-active-workspace` from 104 each to **zero**. Each surviving wake is one `hyprctl --batch` round trip plus `jaq`, tens of milliseconds. **None of it is the idle draw**: no *listener* polls — they block on socket2 or `pactl subscribe`. What *used* to draw at rest was the effectively-ungated `brightness` `defpoll` (next bullet), about two thirds of it — measured 3.75% of a core in reaped children on a daemon whose widget had not yet been hovered **and left**. That is fixed, and brightness now polls at **no** rate at all — it is event-driven (see below) — so what remains is eww's own built-in vars the bar references: `EWW_CPU`/`EWW_RAM`/`EWW_BATTERY` at 2s and `EWW_TIME` at 1s, each forcing a redraw on both bars.
- **A `defpoll`'s `:run-while` does not gate its *start*.** eww begins every script var a window references unconditionally at window-open **and again on every reload** (`open_window` re-adds them without consulting the gate), and evaluates `run-while` only when the gating variable is **assigned** (`update_global_variable` → `apply_run_while_expressions_mentioning`). So a `defpoll` polls at its full interval from window-open until something first assigns its gate **false** — an `:onhover` setting it *true* re-evaluates to true and changes nothing — and a gate mentioning only a variable that nothing assigns never engages at all. **The workaround, if a gated poll is ever needed, is to name the poll's own output variable in the gate** — `:run-while {gate && output >= 0}`, where `>= 0` is always true and exists solely to put `output` into `run_while_mentions`, so the poll's own first tick forces the re-evaluation that stops it. **This config no longer contains a `defpoll` at all**: `brightness` was the only gated one, it ran at 5 Hz from window-open until the first `:onhoverlost` with every reload putting it back, and it is now a `deflisten` on kernel events (next bullet). The trap is recorded because it applies to the next `defpoll` anyone adds, not because anything here depends on it. Note the workaround's own price, which is what drove the move to events: the variable then freezes after one sample, so anything reading it outside the gated widget needs its own source.
- **Brightness is event-driven and per-display.** The kernel's backlight class calls `sysfs_notify()` on `actual_brightness` for every change — **including writes made through logind**, which is the path `brightnessctl` takes here — so `files/eww/scripts/get-brightness` blocks in `poll(POLLPRI)` and never samples. **Reading is what clears the notification**, so every wake must read every fd it registered; seeking alone leaves `POLLPRI` asserted and the loop spins at 100%. One event source is what collapsed the old pair of variables (a fast poll gated to the hover, plus a slow ungated one to keep the icon honest) back into one. It emits **keyed by DRM connector**: `/sys/class/backlight/*/device` resolves to `…/card1-eDP-1/`, and stripping `cardN-` yields exactly the name Hyprland reports and eww passes as `screen`, so nothing hardcodes a monitor. **An external monitor has no backlight device at all** — it is driven over I²C with DDC/CI — so the widget is *hidden* on its bar; before that test existed, the external bar's slider silently moved the laptop panel. Adding real DDC control would need `ddcutil`, `i2c-dev` and an `i2c` group, all system-level in `/persist/etc/nixos`, and DDC round trips are too slow for a 0.2s-feel slider.
- **eww has no `null` literal, and referencing one takes down the whole bar.** `error: No variable named 'null' in scope` aborts the *entire* config load, so no window opens at all and the bars simply never appear — the failure is nothing like a bad property on one widget. Test presence arithmetically: a missing key elvis-defaults, so `{(map?.[key]?.field ?: 0) > 0}` does it.
- **Parse-check before switching, with a throwaway daemon.** `hm-build` proves **nothing** about yuck validity — eww parses at runtime. Instead: `eww -c $(realpath ./result/home-files/.config/eww) daemon --no-daemonize`, then `eww -c … open bar --id t1 --screen <monitor>`. The socket name is hashed from the config directory, so a store path can never collide with the running daemon. Daemon start catches top-level errors; **only `open` exercises the widget tree**, and it is what catches runtime complaints like a bad `:onchange`. Kill with `eww -c … kill`. Do **not** `pkill -f` these — the pattern matches the wrapper shell that ran the command, so it kills only itself and reports success while the target survives.
- **A `scale`'s bounds must be constants, never `deflisten` data.** GTK clamps the value against whatever `:max` holds at the moment it is set, and re-setting `:max` later does **not** lift a value already clamped down. A `:max` derived from listener data is `1 + 1` during the gap between window-open and the listener's first line, so the real reading clamps to 2 and the slider draws empty *permanently*, while a tooltip doing its own arithmetic on the same data reads 100% — the disagreement is the tell. Scale the value to a percentage against constant `:min`/`:max` instead. Relatedly, **`:onchange` fires at window-open**, before that first line, so it runs with empty interpolations: `brightnessctl -d ${… ?: "none"}` makes that run fail harmlessly on a device that cannot exist, where an unguarded `brightnessctl set` would receive the clamped `:min` and dim the panel every time a bar opened.
- **eww kills a handler's command as soon as the handler returns, so anything that waits must detach first.** A `:onclick`/`:onhoverlost` command that sleeps is killed mid-sleep — `files/eww/scripts/close-control-popup` needs a debounce and re-execs itself through `setsid --fork` into its own session to survive. Measured, not inferred: an instrumented build logged `ENTER` on every invocation and never once reached the line after `sleep`, and no stray processes were left behind *because they were being reaped rather than hanging* — so "no hung processes" is evidence FOR this, not against it. Verified fixed by running the script and then `SIGTERM`ing its whole process group; the popup still closed. **Do not remove the `setsid`** — the failure it prevents looks like the logic being wrong, not like a process being killed.
- **A layer window's `:y` is measured from the bottom of any exclusive zone, not from the top of the screen.** The bar reserves a 40px strut (`:exclusive true`), so a popup at `:y "39px"` rendered at **y=78**, leaving a 39px strip where the pointer is over neither window — which dismissed the popup during any slow crossing, and no debounce length could have fixed it. `:y "0px"` puts a popup flush under the bar. Check placement with **`hyprctl layers -j`**, which reports each surface's real `x/y/w/h` — the bar is `x=16 y=9 w=1568 h=30` on eDP-1.
- **`:x` with `:anchor "top right"` is the distance from the monitor's right edge to the window's RIGHT edge.** So centring a window of width `W` on a point `C` is `x = monitor_width - (C + W/2)`. Work in **logical** pixels: eDP-1 is scale 1.20, so it is 1600 wide, not 1920 — using the physical number throws every offset out. **Both** monitors need this now: the external runs 3840x2160 at scale 1.5, so it is 2560 wide, not 3840. It used to be scale 1.0, where the distinction was invisible because physical and logical agreed — so an offset derived before that change can be right for the wrong reason.
- **To find where a widget actually is, log `hyprctl cursorpos` against a hover variable while a human sweeps the pointer.** Nothing in eww reports widget geometry (`eww debug` prints the scope graph). **A warped cursor is useless for this** — `hyprctl dispatch movecursor` teleports without generating the crossing GTK needs, so an automated sweep reports nothing at all and looks like the widget is missing. Two probe attempts were wasted on that before the manual sweep gave brightness 1344 / volume 1362.
- **An undefined SCSS variable fails the WHOLE stylesheet, and it does not look like a CSS bug.** `grass` resolves variables in source order, so a rule placed above its `$var:` definition drops eww to raw GTK defaults — the entire bar goes white and unstyled, which reads as a theming catastrophe rather than one missing rule. **The throwaway-daemon parse check does not catch this**: it validates yuck and reports nothing for a broken stylesheet, writing no log file either. Check separately that every `$var` is defined before use, in both specialisations.

There is one pointer, so one name is sufficient state for any number of bars, and `""` cannot collide with a monitor name. This is why `bar.yuck`'s right-hand section takes `screen` despite otherwise being global.

- **Prefer ANSI-indexed colour over per-app truecolour themes.** A program emitting truecolour bakes fixed hex into the terminal's cells, which (1) makes scrollback permanent — output printed before a darkman switch keeps the old flavour forever, (2) lets long-running processes go stale (fish read its theme once per shell, so a shell open across a transition drew Frappe foregrounds on Latte's background at **1.35:1**, twice as bad as Latte's own palette problem), and (3) scatters the colours so contrast can't be fixed in one place. ANSI-indexed output has none of these: kitty resolves the index at draw time. So `bat` uses `base16` and `fish` uses its built-in defaults, both variant-independent — neither is in the `catppuccin` block in `modules/theme.nix`. (`base16-256` is **not** equivalent; it reaches into the fixed 6×6×6 cube.)
- **No per-program contrast workarounds.** `modules/shell.nix` used to override ten `fish_color_*` slots on Latte, and `modules/theme.nix` pinned delta to `OneHalf{Light,Dark}`; both are gone. Latte's contrast problem is palette-wide — 12 of its 14 accents fall below WCAG AA against its own `base`, while Frappe, Macchiato and Mocha have zero such failures — so patching per app treats one symptom at a time and hides the real state from the audit. Measure with `nix run .#contrast-audit` (see `tools/contrast-audit/`) and fix the palette.
- **The ANSI slots are the leverage point.** Because the above routes most output through `programs.kitty.settings`, one edit reaches bat, fish, fzf, rg, eza's non-gradient columns, delta's syntax and starship at once — and *retroactively*, since ANSI cells store an index and so recolour scrollback that is already on screen.
- **The two grey slots nearest the background are shifted one step along the ramp** (`modules/theme.nix`). Slot names are absolute — 0 is black through 15 is bright white — so which pair hugs the background flips with the variant: `color7`/`color15` on Latte, `color8`/`color0` on Frappe. That ordering is correct by convention; the problem is that base16 themes use those slots as *foregrounds*, so on each variant the two nearest the background end up carrying text. The slot carrying the most text lands on `overlay0` in both flavours, at ΔL 0.250 (Latte) and 0.252 (Frappe) — the same perceptual quietness from mirrored slots, which is why it is a rule and not two tunings. They are deliberately **not** raised to AA: brackets, separators and box drawing should stay subordinate to text you read.
- **The accents are deliberately left alone.** A uniform contrast target is self-defeating, because a contrast ratio *is* a luminance measure: forcing every accent to 4.5:1 forces them all to the same lightness. Measured, mean accent-to-accent contrast collapses 1.49 → 1.02 and the palette reads as one dark mass — chroma barely moves, so what is lost is the lightness spread, not saturation. Latte's yellow 2.31, magenta 2.34 and green 2.96 stay as they are.
- **Do not read the contrast ratio as perception.** WCAG 2.1 is luminance-only: it ignores chroma, so it overstates saturated colours (Helmholtz-Kohlrausch makes them look lighter, hence closer to a light background than the ratio claims), it is blind to polarity, and its `+0.05` floor compresses the dark end — which is why Frappe scores much better than Latte while having *smaller* luminance gaps. Judge by OKLCH ΔL instead; the harness leads with it.
- **Two calibrated thresholds, not one: body ΔL 0.22, glance ΔL 0.07.** Measured with `nix develop .. -c python3 -m contrast_audit.calibrate`, which prints ramps at known ΔL in five hues and asks where reading stops. Body is "would read a screenful without noticing the contrast"; glance is "can read it when I look, but would not want to". Both flavours landed within 0.01 of each other on body, so one pair covers Latte and Frappe. They classify all ten pairs previously judged by eye correctly. Prose and code have to clear body; line numbers, separators and box drawing only have to clear glance, and sitting below body there is the design goal, not a defect — `report.py` holds guide-role pairs to the lower bar for that reason. The difference this makes: Latte shows 88 pairs below 4.5:1 across the fixtures, of which 15 are below body and 3 below glance, and `bat`, `delta`, `fish` and `rg` have none at all in either flavour despite 17 nominal failures between them.
- **No chroma correction — it was fitted and rejected.** `sqrt(ΔL² + (k·Δab)²)` fits the body marks at k≈0.8 with both flavours agreeing to two decimals, which is persuasive and wrong: it scores fzf's green 0.181 against the grey beside it at 0.212, near-equal, for pairs judged "really low" and "okay". The body marks are the least confident tier and the fit read their noise; the confident tier fits k = 0.0–0.3. Plain ΔL is what the harness uses. APCA was also tried and tracks worse than either.
- **hyprshade invalidates colour judgements made between 21:00 and 07:00.** `blue-light-filter.glsl` multiplies every pixel by a 2600 K white point at full strength (R ×1.000, G ×0.651, B ×0.304, in encoded sRGB), and its `LuminancePreservation` block is a no-op — `lum / max(lum, 1e-5)` is 1.0 for any non-black pixel — so nothing offsets the darkening. Latte's `#eff1f5` renders orange (`#ef9d4a`), Frappe's `#303446` brown (`#302215`). A calibration pass taken through it showed a 7× spread across the hue columns that fell to 1.7× once corrected: almost all of the apparent hue effect was the shader. `contrast_audit/shader.py` models it and `calibrate` corrects automatically, parsing the temperature out of whatever `hyprctl getoption decoration:screen_shader` reports (`--filter auto|off|KELVIN` overrides). **`report.py` does not model it yet** — its findings are unfiltered. Since darkman puts Latte on the day side, Latte is essentially never filtered and must be measured with the shader off; Frappe overlaps it for most of its run and wants passes both ways.

A glanceable magnitude cue is the point of the feature; the real fix is upstream.
